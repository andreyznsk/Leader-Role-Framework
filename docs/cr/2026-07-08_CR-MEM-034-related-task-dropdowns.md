``# 2026-07-08_CR-MEM-034: Related Task Dropdowns in Task UI

**Дата:** 2026-07-08  
**Статус:** Implemented  
**Сервис:** MEM / JavaMemoryService  
**Тип:** enhancement  
**Связанный Issue:** #83

## Проблема / Мотивация

В JavaMemoryService уже есть механизм линкования задач через `task_links` и тип связи `RELATES_TO`. Сейчас связь технически существует, но в основном пользовательском сценарии она недостаточно видна.

Когда техлид смотрит список задач на сегодня, ему важно быстро понять, из каких связанных работ состоит большая задача, не открывая каждую задачу отдельно и не переходя в отдельный экран связей.

Также на странице редактирования задачи `/ui/tasks/{id}/edit` связанные задачи должны быть видны внутри существующего блока `Linked Tasks`, чтобы не плодить отдельные UI-блоки и сохранить единое место управления связями.

## Решение

Добавить отображение связанных задач в двух местах UI:

1. `/ui/today` — в карточке задачи добавить раскрываемый блок для задач, связанных с текущей задачей типом `RELATES_TO`.
2. `/ui/tasks/{id}/edit` — встроить отображение связанных задач внутрь существующего блока `Linked Tasks`.

Для MVP отображать только связи типа `RELATES_TO`.

Важно: `RELATES_TO` не вводит строгую иерархию parent/child. Это визуальная группировка связанных задач. Для будущей строгой структуры можно использовать уже существующие типы `PARENT_OF` / `CHILD_OF`.

## UX / UI требования

### `/ui/today`

В карточке задачи:

- если у задачи есть связанные задачи `RELATES_TO`, показать компактную раскрывашку;
- заголовок раскрывашки: `Связанные задачи` или `Linked Tasks` в стиле текущего UI;
- рядом можно показать счётчик связанных задач;
- внутри раскрывашки показать список связанных задач;
- название каждой связанной задачи должно быть кликабельным;
- клик ведёт на `/ui/tasks/{linkedTaskId}/edit`;
- если связанных задач нет — блок не отображать.

Рекомендуемые поля в списке:

- title;
- status;
- priority;
- dueDate/date, если есть;
- assigned person, если есть.

### `/ui/tasks/{id}/edit`

На странице редактирования задачи:

- не создавать отдельный новый блок;
- встроить раскрываемый список связанных задач внутрь существующего блока `Linked Tasks`;
- название связанной задачи должно быть кликабельным;
- клик ведёт на `/ui/tasks/{linkedTaskId}/edit`;
- отображать как исходящие, так и входящие зеркальные связи, чтобы связь была видна с обеих сторон.

## Изменения в API

Новых публичных endpoint-ов для MVP не требуется, если текущие контроллеры и view-model уже могут получить связи через существующий task links service.

При необходимости расширить server-side DTO/model для UI:

- добавить список связанных задач к модели карточки задачи на `/ui/today`;
- добавить список связанных задач к модели страницы `/ui/tasks/{id}/edit`;
- фильтровать связи по `linkType = RELATES_TO`;
- подтягивать краткую информацию о linked task по id.

Существующий контракт task links должен остаться совместимым:

- `GET /api/tasks/{id}/links*` возвращает исходящие и зеркальные входящие связи;
- `direction: OUT | IN` сохраняется;
- reverse mapping не меняется.

## Изменения в схеме БД

Не требуются.

Использовать существующую таблицу:

- `memory.task_links`;
- `link_type = RELATES_TO`.

Миграции в `*/db/migration` не менять.

## Зависимости

- CR-MEM-031 task links должен быть реализован.
- Использовать существующий navigation contract для задач: `/ui/tasks/{id}/edit`.

## Acceptance Criteria

1. На `/ui/today` у карточки задачи отображается dropdown/accordion связанных задач, если есть хотя бы одна связь `RELATES_TO`.
2. На `/ui/today` блок скрыт, если связанных задач нет.
3. В раскрытом блоке на `/ui/today` отображаются связанные задачи с кликабельным названием.
4. Клик по названию связанной задачи ведёт на `/ui/tasks/{linkedTaskId}/edit`.
5. На `/ui/tasks/{id}/edit` связанные задачи отображаются внутри существующего блока `Linked Tasks`, а не отдельным новым блоком.
6. В `Linked Tasks` есть раскрывашка/dropdown со связанными задачами.
7. В `Linked Tasks` название связанной задачи кликабельное и ведёт на `/ui/tasks/{linkedTaskId}/edit`.
8. Отображаются обе стороны связи: исходящие `RELATES_TO` и входящие зеркальные связи.
9. Существующие операции создания/удаления task links не ломаются.
10. Нет изменений схемы БД и новых Flyway migration.

## Как тестировать

### Manual

1. Создать две задачи на сегодня.
2. Связать их типом `RELATES_TO`.
3. Открыть `/ui/today`.
4. Проверить, что у родительской/большой задачи есть раскрываемый блок связанных задач.
5. Развернуть блок и проверить, что связанная задача отображается.
6. Нажать на название связанной задачи.
7. Проверить переход на `/ui/tasks/{linkedTaskId}/edit`.
8. На странице редактирования проверить, что связанная задача отображается внутри блока `Linked Tasks`.
9. Открыть вторую задачу и проверить зеркальное отображение связи.

### E2E

Расширить существующий сценарий:

- `JavaMemoryService/test_e2e/25_task_links.md`

Добавить проверки:

1. создать две тестовые задачи;
2. создать `RELATES_TO` связь;
3. `GET /ui/today` содержит раскрываемый UI-блок linked tasks;
4. `GET /ui/today` содержит ссылку `/ui/tasks/{linkedTaskId}/edit`;
5. `GET /ui/tasks/{id}/edit` содержит блок `Linked Tasks`;
6. `GET /ui/tasks/{id}/edit` содержит кликабельное название связанной задачи;
7. `GET /ui/tasks/{otherId}/edit` показывает зеркальную связь.
